# ノートの「概要」と「ログ」

Project / Goal / Task のノートを、2つに分ける。

- **概要（overview）**：今も正しいこと。目的、方針、決定事項、次の一手。短く保ち、書き換えて最新にする。画面を開くと最初に見え、一覧の抜粋やエージェントの読み取りが既定で返すのはこちら。
- **ログ（log）**：起きたこと。作業の要約、調べたこと、決定に至った経緯。書き足していくもので、長くなってよい。画面では折りたたんであり、エージェントは求めたときだけ読む。

## なぜ分けるか

これまでは、1つの項目にノートが1つだった。

- エージェントの追記（`append_note`）は確認なしでできる一方、書き換え（`replace_note`）は消える操作として扱う。そのため、エージェントは末尾に書き足し続け、誰も要約し直さない。MCP につないでから、ノートは長くなる一方だった。
- 読むときは常に全文だった。`get_task` / `get_goal` はノート全体を返し、`get_context` は配下の Goal・Task のノートを全部並べる。
- プロジェクトの画面では、ノートの下にゴールの一覧がある。ノートが長いと、ゴールにたどり着くまでが遠い。
- 今後チームで使うとき、経緯まで含んだ長いノートを最初に見せることになる。

分けることで、追記の宛先（ログ）と、読むときの既定（概要）が別になる。ログは共有してよい記録として扱う（概要と公開範囲を分けることはしない）。

概要が古くならないようにする仕組みは、今回は入れていない。週に1回、利用者が概要を見直す前提である。週次ノートの画面に「概要の更新以降にログが進んだ項目」を出すことと、エージェントが概要の書き換えを提案できるようにすること（`note_replace` の提案。設計は `agent-mcp.md` にあるが未実装）は、あとで足せる。

## データ

`context_notes` に `section` 列（`overview` か `log`、既定は `overview`）を足し、1つの項目につき `section` ごとに1件にする（マイグレーション 047）。

- 既存のノートは、すべてその項目の概要になる。本文は変えない。
- 一意制約は「項目ごとに1件」（`unique_project_note` など）から「項目と `section` ごとに1件」（`unique_project_note_section` など）に変える。
- ログを別の表にしなかったのは、エディター、画像の添付、検索用の `content_text`、楽観ロック、バックアップをそのまま使うため。ログを1件ずつの行にする案（著者・日時つき）は、ページングや絞り込みには向くが、画面が別物になり、Task では作業ログ（`logs`）と役割が重なる。ログがエディターで扱いにくくなったら考える。

### 既存のノートからログを取り出す（マイグレーション 048）

エージェントの追記には、`エージェントからの追記（日付、名前）` の見出しが付いている。Project と Goal のノートについて、最初の見出しより前を概要に残し、見出し以降をログに移す。

- 文字は消さない。`content_text` も同じ見出しで分ける。ログにだけ出てくる画像は、ログの添付にする。
- **Task のノートは分けない。** Task のノートは Task の本文で、エージェントが作った Task では見出しの下がその本文だからである（提案で `note_markdown` を付けた Task など）。Task の画面で「ノートをコピー」するのも概要なので、本文をログへ動かすと困る。
- Markdown のままのノート、ログにすでに中身のある項目も分けない（2回流しても2回は分かれない）。ログを画面で開いただけの項目には空のログの行ができているが、その行は埋める。
- 見出しより下に利用者が書いた文字も一緒にログへ移る。概要に置きたいものは、エディターで戻す。
- 048 は、新しい API を本番に出したあとで流す。古い API は項目の2つのノートを区別できないため。
- 048 だけを戻す方法はない。047 のロールバックが、すべてのログを概要の末尾に戻す。

## 書く

| 経路 | 既定の宛先 | もう一方へ書くには |
|---|---|---|
| Web のエディター | 開いている方 | 概要の下の「ログ」を開いて書く |
| `append_note`（MCP）、`POST /context-notes/{kind}/{id}/append` | ログ | `section: "overview"` |
| `replace_note`（MCP）、`PUT /context-notes/{kind}/{id}` | 概要 | `section: "log"` |
| `note_append` の提案 | ログ | payload の `section: "overview"` |
| Task を作るときの `description`、提案の `note_markdown` | 概要（Task の本文） | — |
| CLI の `attach --append` | ログ | — |

- 追記を概要に向けるのは、その文字が項目そのものを表すとき（作ったばかりの Task の本文など）に限る。ツールの説明にそう書いてある。
- `replace_note` の `expected_updated_at` は、その `section` のノートの `updated_at`。概要とログは別々にロックする。
- `section` の無い `note_append` の提案（分ける前に届いたもの）は、ログへの追記として扱う。
- **Task のログを書いても、Task の `updated_at` は進まない。** Task が返す `note_excerpt` は概要の冒頭なので、ログでは変わらないため。これで「要約を追記すると、次の `update_task` が 409 になる」ことが無くなり、完了にする順番を気にしなくてよくなった。概要の文字が変わったときは、これまでどおり進む。

## 読む

- **Web**
  - `GET /api/notes/{projects|goals|tasks}/{id}` は概要を返す（これまでと同じ URL）。`?section=log` でログ。`PUT` も同じ。
  - 概要の応答には `log`（`{updated_at, characters}`）が付く。ログに文字があるときだけで、無ければ `null`。画面はこれで、ログを読み込まずに「約1,200文字・最終更新 …」と出す。
- **MCP**
  - `get_task` / `get_goal` は、`note`（概要）と `log`（`{updated_at, characters}`。本文なし）を返す。
  - `get_note`（新設、`notes:read`）は、Project / Goal / Task の概要かログを返す。`tail_characters` を付けると、末尾だけ（段落の切れ目から）を返し、`truncated` で省いたことを示す。Project のノートを直接読む手段は、これまで `get_context` しかなかった。
  - `append_note` は、ノート全体を返すのをやめた（`{section, note: {id, updated_at, characters}}`）。ログは追記のたびに長くなるので、毎回送り返さない。
  - `get_context` は、概要だけを並べ、ログは「約N文字は省略しています」と1行で知らせる。`include_logs: true` で全文を入れる。
- **REST（エージェント）**
  - `GET /context-notes` は、両方を返す（各行に `section`）。`?section=overview` か `?section=log` で絞れる。差分取得はこれまでどおり `updated_at` 順。
  - context export は `include_note_logs=true` でログを入れる。Web のエクスポート画面と CLI の `context --with-logs` も同じ。
- **そのほか**
  - Task の一覧の抜粋（`note_excerpt`）、Task のノートのコピー、AI の下書き（Goal / Task の提案）、週次レポートの背景は、概要だけを使う。
  - Task の検索は、概要とログの両方の文字に当たる。

## 画面

- 概要は、これまでのノートの場所にそのまま出す。
- その下に「ログ（経緯・作業メモ）」を、**閉じた状態**で置く。見出しには、ログの文字数と最終更新を出す（無ければ「まだありません」）。
- 開いたときに初めてログを読み込む。一度開いたら、閉じても編集中の内容は残す（中身は表示しないだけで、作り直さない）。
- ログも、概要と同じエディターと競合のバナーを使う。
- 置いた場所：プロジェクトの画面、ゴールの画面、ノートだけのページ、Task のパネルとページ、Runner の「タスクノート」。
- 提案の受信箱では、`note_append` の提案に「追記する場所（ログ／概要）」を出す。

## 画像

- 画像の添付は、これまでどおり項目（Project / Goal / Task）に対して行う。アップロードした画像は、どちらかのノートが参照するまで、概要のノートが持つ。
- ノートを保存すると、そのノートが参照している画像は、もう一方のノートが持っていたものも含めて、そのノートの添付になる。エディターで概要からログへ画像を移しても、添付は外れない。
- 自分が持つ画像を参照しなくなったとき、もう一方のノートがまだ参照していれば、そちらの添付にする（両方に貼って片方から消した場合）。どちらも参照していなければ、これまでどおり外す（7日後に消える）。もう一方のノートが持つ画像は、ここでは外さない。
- 同じ画像の重複の判定と、枚数の上限（既定 50）は、項目ごと（概要とログの合計）に数える。

## バックアップ

- バックアップの `context_notes` に `section` が入る。分ける前のバックアップのノートは `section` が無く、概要として戻る。
- Task の description と memo を持つ古いバックアップを戻すとき、その文字は概要に入る（ログには入らない）。

## 移行の順番

1. 047 を流す（列と制約。本文は変わらない）。
2. 新しい API と Web を出す。
3. 048 を流す（Project と Goal のノートから、エージェントの追記をログへ移す）。

`migrate.py apply` は 047 と 048 を続けて流すので、使うときはデプロイの直前に流す。古い API が動いている間にログがあると、その項目では概要とログのどちらかが「ノート」として出る。PR のプレビュー（本番のデータベースを使う）でログを書かないこと。

API を戻すときは、047 のロールバックを流す。ログは概要の末尾に戻り、文字は失われない。
