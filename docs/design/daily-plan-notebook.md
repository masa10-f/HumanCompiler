# 日次ノート

日次プランの初期表示は、一続きのノートとして編集する。Enter は改行し、見出し（`# `）、箇条書き（`- `）、チェックリスト（`[ ] `）、強調、引用などはエディタの Markdown 入力ショートカットを使う。予定の前後にもメモを追記でき、自動保存する。

独立した段落で `/schedule` を入力すると、時間帯・割当時間・作業タイプと、プロジェクト・ゴール・タスクの候補を表示する。候補の種類を切り替えたり、名前で検索したりできる。プロジェクトとゴールはタスク未登録でも選択でき、生成時に配下のタスクから自動選択する条件として保存する。該当するタスクがない場合は、生成結果に未配置の理由を表示する。候補をクリックするか、上下キーと Enter で選ぶと、その段落を予定に置き換えて次の段落へ進む。Esc は入力文字列を残して候補を閉じる。`/schedule 13:00-16:00 @タスク名 (90m)` の既存構文も利用できる。`1200-1400 /schedule` と `/schedule 1200-1400` の両方で時間帯を指定でき、`12:00-14:00` の表記も使える。

挿入された予定は時刻とタイトルを中心に表示し、クリックするとタスクの紐付けやプロジェクト・ゴール条件などを編集できる。「自動スケジュール」で生成後も本文を編集でき、生成予定の「実績」から既存のタスク実績・完了操作を使える。ノートの通常のチェックリストはノート内の進捗管理であり、既存のタスクに紐付いたチェック項目の完了操作とは区別する。

編集はノート内で完結する。予定は `/schedule` の候補から挿入し、挿入後の時刻や条件はノート内で編集する。

## 保存と互換性

- 既存の `schema_version: 1` と予定・チェック項目の ID、タスク参照を維持する。
- `text` ブロックに任意の `content`（エディタのノード JSON）を追加し、書式・階層・チェック状態を保存する。`text` は読み取り互換用のプレーンテキストとして併存する。
- 1段落・リストの本文と書式JSONはそれぞれ50,000文字、文書全体はUTF-8のJSONで5MB、500項目、入れ子20階層まで。入力時に上限を検証し、保存できない項目と修正方法を表示する。サーバー側でも同じ上限を検証する。
- 書式・属性を許可リストで検証し、リンクは相対URLと `http` / `https` / `mailto` / `tel` に限定する。
- HTTPで運用する環境でもノートIDを生成できる。
- エディタ内部の `planId` 属性は入れ子も含めて保存前に除去する。APIも旧エディタが送信・保存した同属性を読み書き時に正規化し、箇条書きや引用の保存が検証エラーにならないようにする。文書ブロックのIDは保持する。
- 予定ノードは文書直下に限定し、引用やリストの中に制約が隠れないようにする。
- 生成結果の `source_scheduling_blocks` に生成時の予定条件を保存する。本文やチェックリストの編集では再生成を要求せず、時間帯・対象タスク・条件の変更を検出する。旧生成結果は revision が一致する読込時の条件を画面内で利用する。
- 既存の保存競合・再試行・日付変更前の保存処理を利用する。新しい `content` を古い API が破棄しないよう、API をフロントエンドより先に更新する。履歴検索は下記のマイグレーションを先に適用する。

Markdown は入力ショートカットとして対応する。Markdown ファイル全体のインポート・エクスポート機能は含まない。

## ダッシュボードと独立したノート一覧

ホームとログイン後の移動先は従来の構成を維持し、ダッシュボードを入口にする。ダッシュボードのクイックタスクの下にある「ノート」カードには今日のノートを開くリンク、当日分の本文（見出し・箇条書き・チェック状態・予定を表示）、ほかの日のノート最大3件のプレビュー、独立したノート一覧 (`/notes`) へのリンクを表示する。ノート一覧で履歴・検索・日付絞り込みを利用し、選んだ日の編集画面 (`/scheduling/daily?date=YYYY-MM-DD`) へ移動する。ヘッダーの「その他」からもノート一覧へアクセスできる。

当日分は履歴の上位件数に依存せず、その日付で直接取得する。本文は閲覧用で、編集は「今日のノートを開く」から行う。日付が変わった場合も当日分へ切り替える。

ノート本文はダッシュボードのデータに埋め込まず、専用の `daily_plan_documents` テーブルで日付ごとに管理する。ダッシュボードは同じ履歴APIからプレビューを取得するため、別のノートを複製しない。

ノート横の「ノートの履歴」から保存済みのノートを新しい日付順に開ける。本文・予定名の部分一致検索と日付範囲の絞り込みに対応し、「さらに過去のノート」で20件ずつ取得する。スマートフォンでは「履歴・検索」からパネルへ移動する。前日・翌日・今日への移動と、日付指定でも切り替えられる。日付変更時は現在の編集を保存し、失敗した場合は現在のノートに留まる。ノート・詳細モードともに選択した日付はURLに残るため、再読込やブックマークから同じノートを開ける。

本文の読込はタスク候補の取得を待たない。履歴の検索条件・読み込み済みのページは日付を切り替えても保持する。自動保存後は2秒待って保存したノートのプレビューだけを更新し、一覧をリセットしない。新しい日付の読込に失敗した場合、前日の内容を別の日付へ誤保存しないよう編集を止め、再試行を表示する。

### 履歴APIと展開手順

`GET /api/daily-plans` に `query`（最大200文字）、`date_from`、`date_to`、`before`（排他的な日付カーソル）、`limit`（1〜50、既定20）を渡す。応答は `items`（日付・revision・更新日時・タイトル・一致箇所のプレビュー）と `next_cursor`。認証ユーザーの文書だけを返し、空のノートを除外する。検索語中の `%` と `_` は文字として扱う。内部ID・書式JSONや、ノートに書かれていない生成予定のタイトルは検索対象外。

1. `029_add_daily_plan_search.sql`、`030_trim_daily_plan_search.sql` を順に MigrationManager で適用する。029適用済みの環境には030だけ追加する。トランザクションと既存のバックアップ・検証手順を利用する。
2. API、次にWebをデプロイする。追加の環境変数やパッケージは不要。
3. 既存のノートが検索できること、本文変更が検索に反映されることを確認する。

マイグレーションは `search_text` 列を追加し、既存文書から埋める。030は検索用テキストの前後にある改行・タブ・全角空白などを除去し、空白だけのノートを履歴から除外する。PostgreSQLではトリガーが検索用テキストの正となり、旧APIからの書込みも反映する。Python側の生成処理はSQLite互換用のミラーである。`test_daily_plan_search_postgres.py` と専用CIで、実マイグレーション・ミラーとの一致・旧API書込み・ロールバックを検証する（ローカル実行は `NOTEBOOK_TEST_POSTGRES_URL` でテストDBを指定）。クエリは所有者・日付でDB側で絞り込み、カーソルでページ分割する。部分一致検索は日本語にも対応するが、全文検索インデックスは追加していない。検索対象が非常に多い場合は別途性能検証が必要。

ロールバック時は先にAPIを戻し、030、029の順に各 `_rollback.sql` を適用する。ノート本文や予定データは削除しない。
