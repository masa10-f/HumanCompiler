# エージェントの書き込みと MCP サーバー設計（G4 + G5 の一部）

作成日: 2026-11-03
状態: レビュー待ち（ユーザーの質問への回答と、ビルダー確認の結果を反映済み）
関連: [Agent Gateway 設計（G1 / G2）](agent-gateway.md)、[提案インボックス設計（G3）](agent-proposals.md)、ResearchDistillator `docs/roadmap.md`（Track G の G4 / G5）

## 概要

### 何のためか

ユーザーは普段、ローカルで Claude Code や Codex と一緒に作業し、その後で自分で HumanCompiler を開いて更新している。
エージェントが作業の中身を一番よく知っているのに、それを毎回手で写している。

この設計で、エージェントが MCP 経由で HumanCompiler を**直接**更新できるようにする。
ユーザーが手で書き写す手間を、エージェントに渡すのが目的。

### 作業後に更新しているもの

ユーザーが作業の後に HumanCompiler で更新しているもの（ユーザーの説明、2026-11-03）は次の4つ。

- タスクのステータス
- 新しいタスクの追加
- 既存のタスクの整理
- コンテキストノートの更新。ノートは Project のものが多いが、Goal や Task のノートのこともある

どれを更新するかは、作業ごとに違う。

### 何を作るか

- **Agent API の書き込み（REST）。** エージェントトークンで Goal / Task / ノートを作成・更新できる。
- **MCP サーバー。** HumanCompiler の API に `/mcp` として載せ、Claude Code と Codex からつなぐ。
- **2つのモード（トークンごとに決める）。**
  - **確認なしのモード：** 元の内容が消える操作も、エージェントがその場で直接実行する。
  - **確認するモード：** 元の内容が消える操作だけを、G3 のインボックスへの提案に変える。ユーザーが承認してから実行する。
- **変更の記録と取り消し。** エージェントの書き込みはすべて、前後の値と一緒に記録する。ユーザーは Web の「エージェントの変更」の画面でそれを見て、1件ずつ元に戻せる。

### 前提

G1〜G3 と同じ前提に従う。

- 通信は常にエージェントから始める。
- 複数のユーザーがいる。各ユーザーは、自分のデータと自分のエージェントだけを扱う。どの書き込みも、トークンの持ち主のデータだけに作用する。
- マイグレーションはユーザーが本番 DB に手で適用する。中身は追加だけにし、旧コードと互換にし、2回実行しても安全にする。
- 本番は Fly のマシン1台で、ワーカーも1つ。規模はユーザー本人と、本人のエージェント程度。作り込みすぎを避ける。

### ユーザーが決めたこと（2026-11-03）

| 項目 | 決定 |
|---|---|
| 書き込みの形 | インボックスを挟まず、エージェントが**直接**書き込む |
| 対象 | Task のステータス、Task の追加、既存の Task の整理、Project / Goal / Task のコンテキストノート |
| 元の内容が消える操作 | エージェントが確認なしで実行する**モードも用意する** |
| 依存関係 | Task を足すときに、Task の依存関係（「このタスクはあのタスクの後」）を入れることがある |
| モードの切り替え | **トークンごとに決める**。トークンを作るときに選ぶ |

### 範囲外

- Project の作成・更新・削除
- **完全な削除。** エージェントの「削除」は、すべて「中止（`cancelled`）」への変更にする。完全な削除は、ユーザーが普段の画面で行う。
- 作業セッション、日次ノート、Quick Task の書き込み。Quick Task は既存の `quick_tasks:write` で作れる。
- 作業ログ（Log）の書き込みは、当初は範囲外だったが、後から足した（「作業ログの記録」の節）。
- ノートの画像・添付ファイル（#408）
- Goal の依存関係の書き込み（Task の依存関係だけを扱う）
- HumanCompiler からエージェントに仕事を渡す経路
- Research Distillator からの利用。R3 は G3 の提案を使い、この書き込みは使わない。

## 現状（設計の根拠）

- **エージェントトークン（G1）**
  - スコープは `AgentScope`。
  - プリセットは `AGENT_TOKEN_PRESETS` で定義し、`/scopes` が返す。
  - 書き込みのスコープは `quick_tasks:write` と `proposals:write` だけ。
  - スコープは作成後に変更しない。
  - 監査ログ（`agent_audit_logs`）は、エージェントのリクエストを1件ずつ記録する。
- **Agent Read API（G2）**
  - `/api/agent/v1` に、projects / goals / tasks / quick-tasks / logs / work-sessions / context-notes / daily-plans の取得がある。
  - context-export もある。
  - 書き込みは無い。
- **Web 用の書き込み**
  - Goal：`POST /api/goals`、`PUT /api/goals/{id}`（`GoalUpdate`: title / description / due_date / status）。
  - Task：`PUT /api/tasks/{id}`（`TaskUpdate`: title / description / memo / estimate_hours / due_date / status / work_type / priority / goal_id）。
  - ノート：`PUT /api/notes/{projects|goals|tasks}/{id}` で、ノート全体を置き換える。ノートは対象1つにつき1件。
  - ノートには版の履歴が無い。
  - Task の削除は完全な削除で、作業ログも一緒に消える。
  - 既存のサービス（`goal_service` / `task_service` と、ノートの `get_or_create_note`）が、持ち主の確認をしている。
- **提案インボックス（G3）**
  - `agent_proposals` の `kind` は CHECK で7種類に限られている。
  - 承認すると、`_apply_accept` が実体を作る。
  - 結果は `result_type` / `result_id` に入る。`result_type` も CHECK 付き。
- **MCP。** 依存関係に MCP の SDK は無い。

## 操作と、確認が要る操作

エージェントの書き込みを、2つに分ける。

| 区分 | 操作 | 確認するモード | 確認なしのモード |
|---|---|---|---|
| **ふつうの操作** | Goal の作成（既存の Project の下）、Task の作成（既存の Goal の下） | 直接 | 直接 |
| | Goal / Task の title、estimate_hours、due_date、priority、work_type の変更 | 直接 | 直接 |
| | ステータスを `pending` / `in_progress` / `completed` にする | 直接 | 直接 |
| | Task の依存関係を足す（Task の作成と同時か、後から） | 直接 | 直接 |
| | ノートへの追記（末尾に足す） | 直接 | 直接 |
| | Task の memo への追記（末尾に足す） | 直接 | 直接 |
| **消える操作** | Goal / Task を**中止**にする（`cancelled`。エージェントにとっての削除） | **提案** | 直接 |
| | Goal / Task の description や memo を**書き換える**（追記ではない変更。今の値が空でないとき） | **提案** | 直接 |
| | ノートを**書き換える**（追記ではない変更。整理や要約で書き直す。今のノートが空でないとき） | **提案** | 直接 |
| | Task を別の Goal に**移す** | **提案** | 直接 |
| | Task の依存関係を**外す** | **提案** | 直接 |

**線を引いた理由。**
- 「消える操作」は、ユーザーが書いた文章を消すか、タスクを一覧から外す操作で、間違えると気づきにくい。
- title や数値・日付の変更は、変更の記録から元の値に戻せる。間違えても一覧で目に入る。
- 空の description・memo・ノートに書くのは、何も消さないので「ふつうの操作」になる。空とは、値が無いか、空白だけのこと。HTML のノートは、文字が無いとき（TipTap の `<p></p>` など）。画像や区切り線があれば空ではない。Markdown のノートでは `<…>` も本文なので、空白だけのときに限る。

**`completed` について（私の判断）。**
- `completed` にしても、タスクは一覧に残り、すぐ戻せる。そのため「ふつうの操作」に入れる。
- エージェントが「作業が終わった」と判断して閉じる場面が、一番多い使い方になるはず。

**中止の取り消し。** 中止は、ステータスを戻せば取り消せる。後述の取り消しの機能でも戻せる。

## スコープとプリセット

### 追加するスコープ

| スコープ | 許可する操作 |
|---|---|
| `goals:write` | Goal の作成・更新 |
| `tasks:write` | Task の作成・更新 |
| `notes:write` | Project / Goal / Task のノートへの追記と書き換え |
| `logs:write` | 作業ログ（Log）の記録。後から足した（「作業ログの記録」の節） |
| `writes:unconfirmed` | 「消える操作」を確認なしで実行する。無ければ、消える操作は提案になる |

**提案になるときの条件。**
- 確認するモードで消える操作をすると、それは G3 の提案になる。そのため、`proposals:write` も要る。
- 消える操作をするトークンが、`proposals:write` も `writes:unconfirmed` も持っていなければ、403 を返す。

**監査ログの説明。** `writes:unconfirmed` の説明（`AGENT_SCOPE_DESCRIPTIONS`）には、「中止・書き換え・移動を、承認なしで実行する」とはっきり書く。

### 追加するプリセット

| プリセット | スコープ |
|---|---|
| 作業するエージェント（確認あり） | 読み取りのすべて、`goals:write`、`tasks:write`、`notes:write`、`logs:write`、`proposals:read`、`proposals:write` |
| 作業するエージェント（確認なし） | 上のすべてと、`writes:unconfirmed` |

**モードの切り替え。** モードを変えたいときは、別のトークンを作る。スコープは作成後に変えない、という G1 の規則のまま。

## Agent API の書き込み（REST、`/api/agent/v1`）

MCP のツールと REST は、同じサービス関数を呼ぶ。REST を先に作るのは、テストしやすく、MCP 以外のエージェントやスクリプトからも使えるため。

### エンドポイント

| メソッドとパス | スコープ | 内容 |
|---|---|---|
| `POST /goals` | `goals:write` | Goal を作る。`project_id`、`title`、任意で `description`・`due_date` |
| `PATCH /goals/{id}` | `goals:write` | Goal を更新する。送った項目だけ変える |
| `POST /tasks` | `tasks:write` | Task を作る。`goal_id`、`title`、`estimate_hours`、任意で `description`・`due_date`・`priority`・`work_type`・`depends_on`（先に終わらせる Task の ID の配列） |
| `POST /tasks/{id}/dependencies` | `tasks:write` | 依存関係を足す。`depends_on_task_id` |
| `DELETE /tasks/{id}/dependencies/{depends_on_task_id}` | `tasks:write` | 依存関係を外す（消える操作） |
| `PATCH /tasks/{id}` | `tasks:write` | Task を更新する。送った項目だけ変える |
| `POST /context-notes/{projects\|goals\|tasks}/{id}/append` | `notes:write` | ノートの末尾に Markdown を追記する |
| `PUT /context-notes/{projects\|goals\|tasks}/{id}` | `notes:write` | ノートを書き換える（今のノートが空でなければ消える操作） |

### 共通の規則

**1. 楽観ロック**
- 更新と書き換えのリクエストには、エージェントが直前に読んだ `updated_at` を `expected_updated_at` として必ず付ける。
- 今の値と違えば、409 と最新の状態を返す。エージェントは読み直してからやり直す。
- 追記には付けなくてよい。追記は、他人の変更を消さないため。

**2. 消える操作の判定はサーバーが行う**
- サーバーが、送られた項目と今の値を比べて判定する。
- 中止、空でない description / memo の書き換え、`goal_id` の変更、空でないノートの PUT が、消える操作にあたる。
- 追記の API で書いた分は、ふつうの操作になる。
- トークンが `writes:unconfirmed` を持たなければ、消える操作は書き込まない。代わりに提案を作り、202 と提案（`AgentProposalResponse`）を返す。
- 1回の PATCH に、ふつうの変更と消える変更が混ざっていたら、その全体を1件の提案にする。一部だけを書き込むと、エージェントが状態を誤解するため。

**3. 返す値**
- 直接書き込んだときは、200（作成は 201）と、更新後の実体を返す。

**4. 持ち主の確認**
- 既存のサービスの持ち主の確認を使う。
- 他人のものと存在しないものは、どちらも 404 を返す。区別しない。

**依存関係の規則**
- 既存のサービス（`add_task_dependency`）の確認を使う。持ち主の確認と循環の検出が入る。
- `depends_on` を付けた作成は、Task の作成と依存関係の追加を1つのトランザクションで行う。どれか1つでも失敗したら、何も作らず 422 を返す。循環や、他人の Task のときがこれにあたる。

**5. 入力の上限**
- 既存のモデルの上限に従う（title 200、description 1000、memo 2000 など）。
- 追記1回は2万文字まで。追記後のノート全体には、既存の上限があればそれに従う。

**6. 変更の記録**
- 直接の書き込みは、すべて次の節の `agent_changes` に、同じトランザクションで記録する。

**7. 認証と流量制限**
- 監査ログと流量制限は、既存の Agent API と同じ仕組みを使う。

### ノートの形式

**今の保存の形**
- ノートは Web のエディタ（TipTap）の HTML で保存されている。

**エージェントとやり取りする形：Markdown**
- **読むとき**
  - MCP のツールと、新しい書き込み API の応答では、ノートを HTML から Markdown に変換して返す。
  - 変換に新しい依存関係を足すかどうか（例：`markdownify`）は、実装者が決める。
  - G2 の既存の読み取り API は変えない。
- **書くとき**
  - 追記も書き換えも、Markdown で受け取る。
  - 既存の `note_markdown`（生の HTML を無効にする）で HTML に変換してから保存する。
- **書き換えで失われるもの**
  - Markdown で表せない書式は、書き換えで失われる。例えば文字の色やハイライト。
  - チェックリストの `- [ ]` / `- [x]` は、TipTap のタスクリストの HTML（`<ul data-type="taskList">` と `<li data-type="taskItem" data-checked="…">`）に変換するので残る。すべての項目に印がある箇条書きだけをチェックリストにする。
  - 書き換えで失われるのは、表、文字の色とハイライト、画像と添付。表には対応しない。
  - `replace_note` の説明文にも、失われるものがあることを書く。

**記録と差分**
- `agent_changes` の `before` / `after` には、保存した HTML をそのまま入れる。取り消しで、元とまったく同じに戻すため。
- インボックスの差分では、前後を Markdown に変換してから、行ごとに比べる。HTML のままでは、1行に詰まっていて差分にならないため。

### Web のノート保存の楽観ロック

**直す理由**
- Web のエディタは、編集から2秒後に、ノート全体を版の確認なしで保存している。G3 では「既知の制約」として残した。
- エージェントが作業の終わりにノートへ追記するのは、この設計の一番の使い方になる。そのとき、開きっぱなしのブラウザのタブが古い本文を保存すると、追記が黙って消える。
- しかもこの消え方は `agent_changes` に残らないので、戻せない。
- そのため、この設計で直す。

**直し方**
- Web 用のノート保存（`PUT /api/notes/...`）が、任意で `expected_updated_at` を受け取るようにする。
- エディタは、読み込んだときの `updated_at` を送る。
- 違っていたら 409 を返す。エディタは「別の場所（エージェントなど）で更新されました」と出し、最新を読み込み直せるようにする。
  - 読み込み直すと、ユーザーがまだ保存していない入力は失われる。
  - なので、その入力はコピーできる形で残す。
- Goal / Task の Web の更新は、項目ごとの変更なので、今回は直さない。

**取り消しへの影響**
- ユーザーがノートを一度でも編集すると、本文全体が保存し直される。そのため、それより前のエージェントの追記の取り消しは、ほぼ 409 になる。
- これは受け入れる。追記は、ユーザーが自分の手で消せるため。

### 確認するモードの提案

G3 の `agent_proposals` に、種類を3つ足す。

| 種類 | payload | 承認したときの動作 |
|---|---|---|
| `goal_change` | `goal_id`、`expected_updated_at`、変える項目 | Goal を更新する |
| `task_change` | `task_id`、`expected_updated_at`、変える項目、または外す依存関係 | Task を更新する（中止・移動・書き換え・依存関係を外すことを含む） |
| `note_replace` | 対象（project / goal / task の ID のどれか1つ）、`expected_updated_at`、新しい本文 | ノートを書き換える |

**承認するとき**
- 承認の時点で `expected_updated_at` と今の値を比べる。違えば 409（「提案の後に内容が変わっています」）にし、何も変えない。
- 承認で行った変更も、`agent_changes` に記録する。誰が出した提案かが分かるように、提案の ID を付ける。

**Web のインボックス**
- 変更の前と後を並べて見せる。
- ノートの書き換えは、行ごとの差分で見せる。

**提案の題・理由・冪等キー**
- **題：** サーバーが作る。例えば「タスク『X』を中止」「Project『Y』のノートを書き換え」。
- **理由：** 書き込み API と MCP のツールは、任意で `reason` を受け取り、それを提案の `rationale` にする。
- **冪等キー：** 任意で `idempotency_key` を受け取る。REST では `Idempotency-Key` ヘッダー、MCP ではツールの引数で渡す。
- **キーが無いとき：** サーバーが `auto:{トークンのID}:{対象}:{変更内容のハッシュ}` を作る。タイムアウトの後に同じ変更をやり直しても、提案は増えない。
- **入口：** 新しい3種類は、書き込み API と MCP のツールからだけ作れる。`POST /api/agent/v1/proposals` では受け付けない。変更内容の検証を1か所にまとめるため。
- **未処理の上限：** G3 の上限（200件）は、新しい種類にもかかる。

**編集して承認**
- ノートの書き換えでは、本文の編集を許す。
- `goal_change` と `task_change` は、編集できない種類にする。承認か却下だけ。理由は、前後の差分を正しく見せ続けるため。

## 変更の記録と取り消し

### データモデル: `agent_changes`（新しい表）

| 列 | 型 | 内容 |
|---|---|---|
| `id` | UUID | |
| `user_id` | UUID | 持ち主。どの検索もこれで絞る |
| `actor` | TEXT CHECK | `agent`（エージェントの書き込み・提案の承認）/ `user`（ユーザーによる取り消し） |
| `agent_token_id` | UUID NULL | 書いたトークン。トークンが消えたら NULL。`user` なら NULL |
| `agent_name` | VARCHAR(100) NULL | その時点のトークン名。`user` なら NULL |
| `proposal_id` | UUID NULL | 提案の承認で行った変更なら、その提案 |
| `entity_type` | TEXT CHECK | `goal` / `task` / `context_note` / `task_dependency` |
| `entity_id` | UUID | ノートなら、ノート自身の ID |
| `project_id` | UUID NULL | 変更の時点で対象が属していた Project。Project・Goal・Task の画面での絞り込みに使う |
| `goal_id` | UUID NULL | 同じく Goal（対象が Goal か Task か、そのノートのとき） |
| `action` | TEXT CHECK | `create` / `update` / `append` / `replace` / `revert` |
| `reverts_change_id` | UUID NULL | `revert` のとき、取り消した元の行 |
| `before` | JSONB NULL | 変えた項目の、前の値。作成なら NULL |
| `after` | JSONB | 変えた項目の、後の値 |
| `destructive` | BOOLEAN | 消える操作だったか |
| `reverted_at` | TIMESTAMPTZ NULL | 取り消した時刻 |
| `created_at` | TIMESTAMPTZ | |

**取り消しの記録**
- 取り消しは、新しい1行として記録する。`actor = user`、`action = revert` で、`reverts_change_id` に元の行を入れる。
- 元の行には `reverted_at` を入れる。
- 取り消しの取り消しはできない。もう一度変えたいときは、ユーザーが普段の画面で直す。
- 作成の取り消し（中止にする）も、`revert` として記録する。

**記録する値**
- ノートの `before` / `after` には、本文の全体を入れる。ノートに版の履歴は無いので、これが書き換え前の版になる。
- 追記では、`before` に追記前の文字数、`after` に足した文字列を入れる。全体は入れない。

**保存期間**
- 1年。監査ログの90日より長くする。取り消しの元になる記録だから。
- 期限を過ぎた行は、日次のジョブで消す。

### Web の画面「エージェントの変更」

**一覧**
- 設定画面からも、各 Project / Goal / Task の画面からも開ける一覧。
- Project の画面では、その Project の下の Goal・Task・ノートへの変更をすべて出す。Goal の画面でも同じ。`project_id` / `goal_id` で絞る。
- Task を別の Goal に移す変更は、移す前の Goal にも、移した後の Goal にも出す。前後の値から分かる。
- 新しい順に、時刻、エージェント名、対象、操作、前後の差分を並べる。
- 消える操作には印を付ける。

**取り消し**
- 「元に戻す」は1件ずつ。`before` の値を書き戻し、その取り消しも記録する。
- 取り消しにも楽観ロックをかける。取り消そうとしている変更の後に、同じ項目がまた変わっていたら 409 にし、「後から変わっています」と見せる。この場合、古い変更を上書きでは戻さない。
- 作成の取り消しは、中止にする。完全には消さない。

**ダッシュボード**
- 「エージェントの変更（直近24時間）」の件数を出す。数えるのは `actor = agent` の行だけ。小さく、既存のインボックスのカードの近くに置く。

## MCP サーバー

### 置き場所と方式（私の判断）

**MCP の SDK を使う**
- MCP の SDK（Python の `mcp` パッケージ）を依存関係に足す。
- Streamable HTTP の MCP サーバーとして、既存の FastAPI に `/mcp` で載せる。
- 載せ方は `mount` ではなく `add_route`。`mount` だと、`POST /mcp` が `/mcp/` への 307 になってしまうため。

**DNS リバインディング対策は切る（実装で決めた）**
- SDK の対策は、アドレスだけを信用する（認証のない手元のサーバーを、ブラウザ経由で叩かれる）場合を守るためのもの。
- このサーバーは、すべてのツール呼び出しにトークンが要り、API は Cookie などの自動で付く資格情報を使わない。書き換えられた DNS 名のページには、乗れるものがない。
- ホストの許可リストを置くと、本番・プレビュー・独自ドメインで壊れる原因が増えるだけなので置かない。SDK が POST に求める JSON の `Content-Type` は、そのまま効く。

**この方式を選んだ理由**
- PC ごとに何かを入れたり動かしたりしなくてよい。
- Claude Code も Codex も、URL と Bearer トークンだけでつなげる。
- 認証、持ち主の確認、監査ログ、流量制限は、既存の Agent API と同じものを通る。

**認証**
- `Authorization: Bearer hc_agent_...` で認証する。
- ツールごとに、上のスコープを確かめる。足りなければ、ツールのエラーとして「このトークンにはスコープ X が無い」と返す。

**各ツールの中身**
- REST の書き込みと同じサービス関数を呼ぶ。HTTP で自分自身を呼び直すことはしない。

**監査ログと流量制限**
- 今の監査のミドルウェアとスコープの依存関数は、`/api/agent/` の FastAPI のルートにしか効かない。そこで MCP では、ツールの呼び出しを受ける入口で、同じ関数（トークンの検証、スコープの確認、監査ログの書き込み、流量制限）を明示的に呼ぶ。
- 監査ログは、HTTP のリクエストごとではなく、**ツールの呼び出しごとに1行**にする。`route` に `mcp:<ツール名>`、`required_scope` にそのツールのスコープを入れる。トークンの監査ログの画面で、何をしたかが読めるようにするため。
- ツールを持たない MCP のやり取り（初期化 `initialize`、ツールの一覧 `list_tools`）は、サーバーの説明を返すだけでトークンを要さないため、**監査も流量制限もしない**（実装で決めた。当初は `mcp:initialize` などで記録する案だった）。
- 流量制限（トークンごとに1分120回）は、ツールの呼び出しの回数で数える。超えたときのツールのエラーは、REST の 429 と同じ `status` と `detail` に加えて、待つ秒数 `retry_after` を持つ（MCP には `Retry-After` ヘッダーを付ける場所がないため）。

**ツールのエラーの形**
- 失敗は、`{"status": <数>, "detail": ...}` の JSON をテキストにしたツールのエラーとして返す。`status` と `detail` は REST と同じ（401・403・404・409・422・429）。想定外の例外は `{"status": 500, "detail": "Internal error"}`。
- ツールの入力スキーマに合わない引数は、ツールの関数に届く前に MCP の層が弾く。この場合は、上の JSON ではなく、MCP の層のテキストのエラーになる（監査もしない）。

### ツール

| ツール | 必要なスコープ | 内容 |
|---|---|---|
| `find` | 探す種類の読み取り（`projects:read` / `goals:read` / `tasks:read`。種類を指定しなければ3つすべて） | Project / Goal / Task を題で探す。部分一致。各候補の ID、親、状態を返す |
| `get_context` | `context:read` | Project か Goal の context export（Markdown）を返す。作業を始める前に読む想定 |
| `get_task` / `get_goal` | `tasks:read` / `goals:read` | 1件と、そのノートを返す。ノートは REST と同じく `notes:read` があるときだけ返し、無ければ `null` |
| `create_goal` / `create_task` | `goals:write` / `tasks:write` | 作る |
| `update_goal` / `update_task` | `goals:write` / `tasks:write` | 送った項目だけ変える。`expected_updated_at` が必須 |
| `add_dependency` / `remove_dependency` | `tasks:write` | Task の依存関係を足す・外す。`create_task` も `depends_on` を受け取る |
| `append_note` | `notes:write` | Project / Goal / Task のノートに追記する |
| `replace_note` | `notes:write` | ノートを書き換える。`expected_updated_at` が必須 |
| `list_logs` | `logs:read` | Task の作業ログを新しい順に返す。件数と合計の分も返す |
| `create_log` | `logs:write` | Task に作業ログ（作業時間と作業内容）を記録する |
| `list_my_changes` | 不要（認証は要る） | このトークンが最近行った変更と、出した提案の状態。自分のトークンの行だけなので、スコープは問わない。提案は `proposals:read` があるときだけ返し、無ければ空のリスト |

**消える操作を含むツール**
- 結果が「書き込んだ」か「提案にした」かを、必ず返す。提案にしたときは、提案の ID と「ユーザーの承認待ち」を返す。
- エージェントが提案を「済んだ」と誤解しないようにするため。

**ツールの説明文で、エージェントに次のことを求める**
1. 書き込みの前に、対象を `find` や `get_*` で確かめる。
2. 作業の終わりに、関係するタスクのステータスとノートを更新する。
3. ノートには、ユーザーが後で読んで分かる要約を、日付つきで追記する。
4. 書き換えは、整理を頼まれたときだけにする。

### 使い方の案内

設定画面のエージェントトークンの使い方ガイドに、MCP の節を足す。

- **Claude Code：** 先に、プロジェクトの `.mcp.json` の `headers` に `"Authorization": "Bearer ${HUMANCOMPILER_TOKEN}"` と書く形を載せる（`url` は `https://humancompiler-api-masa.fly.dev/mcp`）。`${...}` は、Claude Code がファイルを読み込むたびに環境変数から展開されるので、トークンの値は設定に残らない。ファイルには変数名だけが入るため、コミットしても安全。プロジェクトのサーバーは、初回に Claude Code が承認を求める。
  - その後に、手早く試すための代替として `claude mcp add --transport http humancompiler https://humancompiler-api-masa.fly.dev/mcp --header "Authorization: Bearer ${HUMANCOMPILER_TOKEN}"` を載せる。ダブルクォートの中の `${...}` は、シェルが先に展開するため、トークンの値が `~/.claude.json` に保存される。ガイドでは見出しにその旨を書く。
- **Codex：** `~/.codex/config.toml` の `[mcp_servers.humancompiler]` に、`url` と、トークンを読む環境変数（`bearer_token_env_var`）を書く形。
- **トークンの扱い：** トークンはファイルや環境変数に置く。設定ファイルやチャットに直接書かない、と注意書きを出す。

コマンドと設定の書き方は、両方のクライアントの最新の文書で確かめた（Claude Code：https://code.claude.com/docs/en/mcp 、Codex：https://developers.openai.com/codex/mcp ）。Codex の `url` と `bearer_token_env_var` は、文書どおりのキー名。

## 作業ログの記録（2026-11-04 追加）

**何のためか**
- ユーザーは、作業ログ（Log）の `comment` に作業内容を書くことが多い。エージェントが作業の中身を一番よく知っているので、作業時間と一緒にエージェントに記録させる。

**スコープ**
- `logs:write` を新しく足す。`tasks:write` には含めない。スコープは作成後に変えない、という G1 の規則のとおり、今あるトークンの権限を黙って広げないため。
- 「作業するエージェント」の2つのプリセットに入れる。今あるトークンで記録したいときは、トークンを作り直す。

**操作**
- REST：`POST /api/agent/v1/logs`（`task_id`、`actual_minutes`、任意で `comment`）。201 と、作ったログを返す。
- MCP：`create_log`。結果は `{log, task}`。`list_logs`（`logs:read`）で、同じ作業を二重に記録していないかを先に確かめられる。
- 入力の上限：`actual_minutes` は 1〜1440 分（Web には上限が無いが、エージェントの桁の間違いを止めるため）。`comment` は既存の列と同じ 500 文字。
- 追加だけで、何も消さないので「ふつうの操作」。確認するモードでも直接書き込む。
- 作業ログの更新・削除はしない。間違えたときは、ユーザーが普段の画面で直す。

**Task のステータス**
- Web と同じく、`pending` の Task に記録すると `in_progress` になる。
- これで Task の `updated_at` が変わるので、MCP の結果には今の Task を入れる。エージェントは続けて `update_task` を呼ぶときに、その `updated_at` を使う。

**変更の記録**
- ログの作成は `agent_changes` に `entity_type = log`、`action = create` で残す。`after` には `task_id`、`actual_minutes`、`comment`。
- ステータスが変わったときは、Task の `update` の行（`status` の前後）も別に残す。
- `entity_type` の CHECK に `log` を足すマイグレーション `041_add_agent_log_changes.sql` を足す。追加だけで、2回実行しても安全。ロールバックは `log` の行を消してから、CHECK を 040 の4種類に戻す（作業ログ自体は残る）。

## マイグレーション（`040_add_agent_writes.sql`）

**表の追加**
- `agent_changes` の表と索引を足す。
- 索引は `(user_id, created_at)`、`(entity_type, entity_id)`、`(user_id, project_id, created_at)`、`(user_id, goal_id, created_at)`。

**提案の種類**
- `agent_proposals.kind` の CHECK に、`goal_change`、`task_change`、`note_replace` を足す。
- 制約は名前で落としてから、作り直す。
- 旧コードは新しい種類を作らないので、互換のまま。

**結果の種類**
- `agent_proposals.result_type` の CHECK に、`goal_change`・`task_change`・`note_replace` の結果を表す値を足す。
- 新しい種類の承認の結果は、`result_type` に対象の種類（`goal` / `task` / `context_note`）、`result_id` に対象の ID を入れる。既存の値で足りるかを実装のときに確かめ、足りなければここで足す。

**その他**
- `IF NOT EXISTS` で書き、2回実行しても安全にする。
- 対になるロールバックのファイルも作る。

## セキュリティ

- **持ち主の確認：** すべての書き込みは、持ち主の確認を通ったサービス関数だけで行う。ID を推測しても、他人のデータには 404 しか返らない。
- **完全な削除はしない：** エージェントは完全な削除をできない。最悪でも中止と書き換えで、どちらも `agent_changes` から戻せる。
- **確認なしの強さ：** `writes:unconfirmed` は強いスコープなので、トークンを作る画面で警告を出す。
- **エージェントの書いた文字列は信頼しない：**
  - Web では、プレーンテキストか、生の HTML を無効にした Markdown として表示する。G3 と同じ。
  - ノートへの追記は、既存の `note_markdown` の変換を通す。
- **トークンをログに出さない：** トークンの値は、ログ、エラー、ツールの結果のどれにも出さない。
- **プロンプトインジェクション：** ツールの結果に入るユーザーのデータ（ノートの本文など）は、エージェントにとって「指示」ではなく「データ」。ツールの説明文にもそう書く。これは HumanCompiler の側では防ぎきれない。だから消える操作は記録して戻せるようにし、強いモードはトークンごとに選ぶ形にしている。

## テスト

### バックエンド（pytest）

- **スコープ**
  - 書き込みのスコープが無ければ 403。
  - 消える操作で、`proposals:write` も `writes:unconfirmed` も無ければ 403。
- **ふつうの操作**
  - 作成、更新、追記が直接書き込まれ、`agent_changes` に前後の値が残る。
- **消える操作**
  - 確認するモードでは書き込まれず、提案（`goal_change` / `task_change` / `note_replace`）ができて 202。
  - 確認なしのモードでは直接書き込まれる。
  - ふつうの変更と消える変更が混ざった PATCH は、全体が1件の提案になる。
- **楽観ロック**
  - `expected_updated_at` が違えば 409 で、何も変わらない。
  - 提案の承認のときも同じ。
- **依存関係**
  - `depends_on` 付きの作成で、依存関係も一緒にできる。
  - 循環や他人の Task なら 422 で、Task も作られない。
  - 外すのは、確認するモードでは提案になる。
- **持ち主**
  - 他人の Goal / Task / ノートは 404。
  - 他人の Goal の下に Task を作ろうとすると 404。
- **ノート**
  - Markdown で追記・書き換えができる。
  - 読むときは Markdown で返る。
  - Web の保存で `expected_updated_at` が違えば 409 になる。
- **提案の重複**
  - 同じ変更をキーなしで2回送っても、提案は1件。
- **取り消し**
  - `before` が書き戻され、取り消しが `actor = user`、`action = revert` の行として記録される。
  - 後から同じ項目が変わっていれば 409。
  - 作成の取り消しは中止になる。
- **MCP**
  - ツールの一覧が返る。
  - スコープが無いツールはエラーになる。
  - 消える操作のツールは「提案にした」を返す。
  - ツールの結果にトークンが出ない。
- **マイグレーション**
  - Postgres の CI で、040 を2回適用できる。
  - 新しい種類の提案を保存できる。

### フロントエンド（Jest）

- インボックスで、新しい3種類の提案の前後の表示、ノートの差分、承認と却下ができる。
- 「エージェントの変更」の一覧、取り消し、409 のときの表示。
- トークン作成画面の新しいプリセットと、`writes:unconfirmed` の警告。
